# ft-021 渲染分级 + drawio 单篇图谱

## 目标

把渲染层从「邮件 HTML 一种形态」拓展为**分级速读卡片 + drawio 单篇图谱**。
桌面 app 形态（v1.0）需要本地可消费的 artifact，邮件不再是唯一出口。

## 三档速读卡片

| 档 | 内容 | 用户场景 |
|---|---|---|
| **L0** | 一句话结论 + 主图（figure_picker 选出的 cover） | 信息流扫读 |
| **L1** | claim 卡：每条 claim 一格，附 evidence 缩略图 + counter_signal 标记 | 看「这篇说了什么 + 哪里可疑」 |
| **L2** | 完整 claim/evidence/counter_signal 列表 + drawio 图谱链接 | 真要精读时跳转 |

## drawio 单篇图谱

**节点**（来自 ft-019/ft-020）：
- `claim`（来自 `interpret_claims`）
- `figure` / `table` / `citation`（来自 `extract_*`）
- **不入图**：`equation`、`section`（避免视觉过载；equation 在 claim 卡内可点开）

**边**：
- `supports`：claim → evidence material（来自 L1 claim_evidence）
- `contradicts`：counter_signal → claim（来自 L2）
- `cites`：claim → citation（如果 claim 段落引了某 prior work）

**输出**：`render_artifacts` 表 + `media/render/<paper_id>/graph.drawio` 文件。
直接生成 drawio 标准 XML（mxGraphModel），用户用本地 drawio app 打开即可。**不嵌编辑器**。

## 表结构

```
render_artifacts:
  artifact_id (pk)
  paper_arxiv_id
  artifact_type   (card_l0 / card_l1 / card_l2 / drawio_graph)
  payload_path    (相对 media/render/...)
  payload_meta    (json: 渲染参数、生成时间)
  created_at
```

## 接口契约

```python
# render/base.py
class Renderer(Protocol):
    def render(self, paper_arxiv_id: str, level: Literal["L0","L1","L2","drawio"]) -> RenderArtifact: ...
```

## 现有 delivery 的关系

`delivery/` **保持纯传输层**：把 render artifact 作为输入，按渠道格式化（邮件 HTML / 飞书卡片 / 微信图文）。
具体地：
- `delivery/email_renderer.py` 重构为「读 L1 卡 + 内嵌 figure → email HTML」
- 飞书 / 微信渲染同理读 render artifact

## CLI

```
python manage.py render_paper <arxiv_id> --level L1
python manage.py render_paper <arxiv_id> --level drawio   # 输出 .drawio 文件路径
```

## 验收标准

1. 一篇有 L1+L2 解读的 paper，能产出 L0/L1/L2 三档卡片 + drawio 文件
2. 生成的 .drawio 文件用本地 drawio 打开能正确显示节点和边
3. 邮件流程切换到读 L1 卡，外观不退化
4. `render_artifacts` 表幂等：同 paper + 同 level 重生成覆盖而非追加

## 风险

- drawio XML 节点布局：MVP 用简单分层布局（claim 一行、evidence 一行），不做力导向；后续可换 mxgraph autolayout
- L2 卡片信息量大可能臃肿：限定 top-K claim（按 confidence + counter_signal 数量排序）
- 邮件渲染重构可能引入回归：保留旧渲染路径作为兜底 flag，回归测试通过后再切

## 工作量估计

- 0.5 天：models + Renderer 接口
