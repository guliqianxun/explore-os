# ft-016 DeliveryAdapter 抽象层

## 重新定位
explore-os 的核心是**内容生产**，投递只是最后一公里。
后端要支持邮件 / 飞书 / 微信订阅号三种渠道，所以必须抽象统一接口。

## 设计

`delivery/base.py`：

- **`Digest`**（渠道无关）：subject + run_summary + narrative + deeps + skims + inline_images
- **`DeliveryTarget`**：channel + to + params（按渠道解释）
- **`DeliveryResult`**：success + detail + metadata
- **`DeliveryAdapter` Protocol**：`key` + `deliver(digest, target) -> result`
- **`REGISTRY`** + `register()` + `get()`：与 `sources.base` 同模式

`delivery/adapters/`：
- `email.py` ✅ 实现（迁自原 email_renderer + email_sender）
- `feishu.py` 占位（ft-017）
- `wechat_subscription.py` 占位（ft-018）

`delivery/__init__.py` 导入三个 adapter 触发 register。

## Pipeline 改动
`run_subscription` 不再直接调 SMTP。流程：
1. 准备 `Digest`（含 inline_images 文件路径，cid/media_id 由各 adapter 自行处理）
2. 遍历 `sub.deliveries`，按 `d.channel` 从 REGISTRY 取 adapter
3. 调 `adapter.deliver(digest, target)` → 收 result 写日志

## 兼容性
- `delivery/email_renderer.py` / `email_sender.py` 保留为 thin wrapper 重导出，老代码无须改
- 旧 `RenderedDeep` / `RenderedSkim` 移到 base.py，原模块再导出

## 验收

- `run_subscription` 通过 registry 路由 email ✅，feishu/wechat 调用返回 not_implemented ✅
- email 实战发件路径不变 ✅
- 全量 118 tests passing
