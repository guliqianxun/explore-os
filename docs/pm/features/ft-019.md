# ft-019 抽取器素材索引层

> **战略意义**：把项目从「论文日报 pipeline」升级为「论文理解中台」的第一段。
> 抽取器是后续解读器（ft-020）和渲染器（ft-021）共用的素材底座。

## 目标

把当前散落在 `interpret/` 下的 PDF/caption/figure 解析能力**重构成独立的 `extract` Django app**，
按统一接口产出五类确定性 material，落库为可寻址的一等公民（每条带稳定 `material_id`）。

**严格边界：抽取器不产 claim、不做语义理解。** 所有语义任务交解读器。

## 五类 Material

| 类型 | 表名 | 关键字段 |
|------|------|---------|
| section | `extract_sections` | paper_id, path（如 `3.2 Method`）, level, char_offset_start/end, raw_text |
| figure | `extract_figures` | paper_id, fig_label（"Figure 1"）, page, bbox, caption, image_path |
| table | `extract_tables` | paper_id, tbl_label, page, bbox, caption, raw_text/html |
| equation | `extract_equations` | paper_id, eq_label（可空）, page, bbox, latex_or_text, inline_or_display |
| citation | `extract_citations` | paper_id, bibkey, raw_text, title（best-effort 从 bibtex 抽）, year |

**material_id 规则**：`<paper_arxiv_id>:<type>:<seq>`，例：`2401.12345:figure:3`。

> **citation 解析深度**：MVP 仅存 bibkey + 标题 + 年份。**arXiv id / DOI 反解作为独立异步任务**，不在本 ft 范围。

## 同库不同前缀

不使用 PG schema，所有表用前缀区分归属（兼容 SQLite 切换）：

```
extract_sections / extract_figures / extract_tables / extract_equations / extract_citations
interpret_*    （ft-020 引入）
render_*       （ft-021 引入）
```

Django app 仍按段切：`apps/extract/`、`apps/interpret/`、`apps/render/`。

## 接口契约

```python
# extract/base.py
class Extractor(Protocol):
    def extract(self, paper_pdf_path: Path, paper_arxiv_id: str) -> ExtractResult: ...

@dataclass
class ExtractResult:
    sections: list[SectionMaterial]
    figures: list[FigureMaterial]
    tables: list[TableMaterial]
    equations: list[EquationMaterial]
    citations: list[CitationMaterial]
```

每个 Material dataclass 必含：`material_id`、`paper_arxiv_id`、`type`、`bbox`（如适用）、`raw_payload`（jsonb）。

## 验收标准

1. `python manage.py extract_paper 2401.12345` 跑通，写入五类 material 到库
2. 同一篇 paper 重复 extract 幂等（material_id 稳定，不重复插入）
3. material 表均无 PG-only 字段（`ArrayField` / PG `tsvector` 等），全部用 `JSONField` 抽象
4. 既有 ft-013/014 主流程不破：`run_subscription` 仍能跑出邮件（解读器临时直接读 `extract_*` 表）
5. 单元测试 + 端到端测试全绿
