# ft-001 订阅配置 schema

## 目标
定义订阅的数据模型与配置格式。这是整个项目的核心领域对象，决定下游所有模块接口形状。

## 设计

### 领域模型（Django models，Postgres）
- `Subscription`：`id / user_id / name / interests(JSON) / enabled / created_at`
- `SubscriptionSource`：`subscription_id / source_key(arxiv|hf_papers|...) / params(JSON)`
- `SubscriptionDelivery`：`subscription_id / channel(email|feishu) / depth(tldr|deep) / schedule(cron) / params(JSON)`
- `SubscriptionRun`：每次执行的快照（触发时间、涉及 source、新增条目数、成本），详见 ft-005。

一对多：订阅 → sources / deliveries，支持"一订阅多源多渠道"。

### 配置入口
MVP 双通道：
- YAML 文件（自用便捷）→ `manage.py sync_subscriptions <file>` 导入/更新 DB。
- REST API（Postman 测）→ `POST /api/subscriptions`，产品化直接复用。

YAML 样例：
```yaml
subscriptions:
  - name: diffusion-daily
    interests: ["diffusion model", "flow matching"]
    sources:
      - key: arxiv
        params: {categories: [cs.CV, cs.LG]}
      - key: hf_papers
    deliveries:
      - channel: email
        depth: tldr
        schedule: "0 8 * * *"
```

### 分组预留
渲染阶段按 `source.group`（papers / code / models）归类。MVP 所有 source 都是 papers 组，但模型字段与渲染器从一开始支持分组。

## 验收
- `sync_subscriptions` 幂等：同名订阅重复导入=更新。
- REST API 可 CRUD 订阅，Postman 通。
- 订阅 schema 校验失败有清晰错误。

## 风险
- interests 自由文本 vs 结构化关键词：MVP 允许两者混存（list[str]），rewriter 统一处理。
