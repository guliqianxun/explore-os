# ft-022 单机 app packaging 调研

> **本 ft 仅产出决策文档，不动业务代码。**

## 目标

为 v1.0 「explore-os 桌面单机 app」选型 + 评估 packaging 路径。
**首选 Tauri，Electron 作为兜底**——两条路都要把可行性、包体、Python 集成成本算清楚。

## 调研产出

最终输出 `docs/architecture/packaging.md`，包含：

### 1. Tauri 路径评估
- Sidecar 启 Python（PyInstaller 打包 Django）的可行性
- Tauri ↔ Python 通信方式（HTTP localhost vs stdio）
- 包体大小预估（Rust 壳 + WebView + Python runtime + 依赖）
- 跨平台：Windows / macOS / Linux 打包流程
- 已知 sidecar 失败模式（Python runtime 路径、依赖缺失、防火墙拦本地端口）

### 2. Electron 兜底评估
- electron-builder + Python sidecar 的成熟方案
- 包体差距（vs Tauri）
- 切换 Tauri → Electron 的代价：前端代码若用标准 Web 技术则迁移成本低

### 3. Django → SQLite 切换路径
- 现有 PG 表结构兼容性扫描（找出潜在 PG-only 用法）
- ORM 层无需改动的部分 vs 需手工 patch 的部分
- 数据迁移：用户首次启动时 SQLite 空库，从订阅 yaml + media 文件冷启动

### 4. 桌面端调度器
- 桌面端不依赖系统 cron。备选：APScheduler in-process / Django-Q（依赖 Redis，桌面端不合适）
- 推荐方案 + 用户「立即抓取」按钮

### 5. 风险清单
- 防火墙 / 杀毒软件对 localhost sidecar 的拦截
- Python runtime 体积（~80MB+）与 Tauri 轻量壳的悖论
- 自动更新机制（Tauri updater vs electron-updater）

## 验收标准

1. `docs/architecture/packaging.md` 完成，至少回答上述 5 大块
2. 给出明确的「Tauri 失败决策点清单」——满足任一则切 Electron
3. 列出当前代码库中**违反单机 app 假设**的耦合点（如 hardcoded SMTP 必填、PG-only 字段），形成后续清理 backlog
4. 不做实际打包尝试（v1.0 启动时再做）
